# Empório da Música customer service agent

A text-based customer service agent for Empório da Música, a fictional musical instrument
store in Campo Grande/MS. It answers customers in Brazilian Portuguese, looks up products,
prices, payment options and orders in the store data, and applies the store policy manual.

Built for the Artefact AI Engineer technical challenge.

- **Approach:** OpenAI-compatible function calling with a hand-written loop (no agent framework).
- **Data:** the provided CSVs, loaded into typed in-memory objects and exposed only through tools.
- **Policies:** the PDF manual split into its 10 sections, served by topic.
- **Interface:** CLI.
- **Examples:** five real conversations in [`examples/`](examples/).

## Quick start

Requirements: Python 3.11+ and [uv](https://docs.astral.sh/uv/getting-started/installation/).

```bash
git clone <repo-url> emporio-agent
cd emporio-agent
uv sync                       # creates .venv and installs dependencies
cp .env.example .env          # then set OPENAI_API_KEY in .env
uv run emporio-agent          # chat in the terminal
```

CLI options:

```bash
uv run emporio-agent --debug              # also print the tools called in each turn
uv run emporio-agent --save conversa.md   # save the conversation as Markdown on exit
```

Inside the chat, `/novo` starts a new conversation and `/sair` quits.

Other commands:

```bash
uv run pytest                            # 133 tests, no network, no API key needed
uv run ruff check && uv run ruff format --check
uv run python scripts/run_examples.py    # regenerate examples/ (calls the API; pass 03 for one)
uv run python scripts/build_policies.py  # rebuild data/processed/policies.json from the PDF
```

Without uv: `python -m venv .venv`, activate it, `pip install -e .`, then run `emporio-agent`.

### Model and provider

| Variable | Default | Notes |
| --- | --- | --- |
| `OPENAI_API_KEY` | (required) | |
| `OPENAI_BASE_URL` | `https://api.openai.com/v1` | Any OpenAI-compatible endpoint (Groq, OpenRouter, Ollama...) |
| `MODEL` | `gpt-5.4-mini` | Must support tool calling |

Only OpenAI models were tested. Other providers should work through `OPENAI_BASE_URL`, but
small local models tend to be much less reliable at choosing tools.

## How it works

```text
customer message
      │
      ▼
 Agent.ask()  ── system prompt (rules + current date/time) + history + tool schemas ──► LLM
      ▲                                                                                  │
      │                         tool calls (0..n, possibly parallel, max 6 rounds)       │
      │   ◄──────────────── JSON results ◄──── tools.py ◄────────────────────────────────┘
      │                                          │
      │                     data_store.py (CSVs) · policies.json · clock · holidays
      ▼
 reply in Portuguese
```

| Tool | Answers | Business logic in Python |
| --- | --- | --- |
| `search_products` | "Quais violões até R$1000?", "Quanto custa o GD20?" | Accent-insensitive search, price filter on the price actually paid, availability status, alternatives for an unavailable exact match |
| `get_product_details` | Specs, description, promotion | Alternatives (same category, ±30% price) for unavailable products |
| `list_categories` | "O que vocês vendem?" | |
| `calculate_payment_options` | "Quanto fica no PIX? E em 10x?" | PIX 5% not stacked with promotions, installment minimums per bracket, combined payment above R$ 2.000 |
| `get_order_status` | "Cadê meu pedido?", "Posso devolver?" | Identity check (LGPD), overdue detection, return/exchange/warranty windows from today's date |
| `get_policy` | Returns, warranty, shipping, payment methods, address | Returns one manual section by topic |
| `get_store_status` | "Estão abertos agora?" | Opening hours, national and state holidays, next opening |

The rule that drives the design: **the model never produces a fact**. Prices, dates, deadlines,
discounts and installment values are computed and formatted by code; the model chooses tools
and writes the reply. This is what policy 7.1 asks for ("nunca fornecer informações sobre
preços, estoque ou prazos sem consultar o sistema") and it is the easiest kind of behavior to
test.

## Technical decisions

**Function calling, no framework.** The questions customers ask map to a handful of
well-defined lookups. Function calling lets the model decide *when* to consult data and *which*
policy to read, while every lookup stays a typed, testable Python function. The loop is about
60 lines ([`agent.py`](src/emporio_agent/agent.py)); a framework (LangChain, LlamaIndex) would
add abstractions without adding capability at this size, and would make the loop harder to
explain and debug.

**Why not an SQL agent.** Letting the model write SQL over the order and customer tables would
make the LGPD check optional (a query can join customers without verifying anyone) and opens
the door to wrong or unsafe queries. With tools, `get_order_status` cannot return data without
a matching e-mail or phone, whatever the model does.

**Why not RAG with embeddings for the policies.** The manual has 8 pages and 10 clearly titled
sections. Splitting by section and letting the model pick a topic from an enum is exact,
cheap and debuggable (the transcript shows which section was read). With dozens of documents
or free-form content, I would move to chunked retrieval with embeddings.

**Data handling.** 65 products and 20 orders fit in memory as dataclasses
([`data_store.py`](src/emporio_agent/data_store.py)). Money is `Decimal`; availability is
derived in one place, where `discontinued` and `coming_soon` override stock. Only the active
promotion affects a price. Expired promotions are kept in a separate `expired_promotions` field,
marked as not valid, so the agent can tell a customer that a promotion ended instead of
hedging.

**Prices shown to the customer.** Tools return a `price_display` string built by code, e.g.
`R$ 439,20 (de R$ 549,00, 20% de desconto)`, and the prompt requires copying it literally. A
prompt rule alone ("always show original price and %") was followed only about half the time
in PIX answers.

**Model.** `gpt-5.4-mini`. I started with `gpt-4.1-mini` and compared both on the same
scenarios: the older model asked for e-mail *and* phone when either is enough, called a
customer by a name guessed from an e-mail that failed verification, and read the estimated
delivery date as a ship date. `gpt-5.4-mini` did none of these at about 1.5 s per turn.
No `temperature` is sent, so reasoning models work unchanged.

**Prompt strategy.** One system prompt ([`prompts.py`](src/emporio_agent/prompts.py)) with:
persona and tone from policy 7.1; an explicit map of question type → tool; product, promotion
and order rules; complaint and escalation handling; scope and prompt-injection rules. It is
written in English and requires replies in Brazilian Portuguese. It is rebuilt every turn with
the current date and time in Campo Grande, because store hours and return windows depend on it.
Where a prompt rule proved unreliable in testing, the behavior moved into a tool (e.g.
alternatives are returned together with an out-of-stock match).

**Conversation history.** Kept in memory for the session, so follow-ups like "e no PIX?" work.
Not persisted across sessions: the challenge does not need it, and a real deployment would
store it per customer in the messaging channel's backend.

**Interface.** A CLI. The focus is the agent; a CLI keeps testing and transcript generation
trivial.

Every smaller decision is one line in [`docs/decisions.md`](docs/decisions.md).

## Data notes and assumptions

The data has inconsistencies, some clearly on purpose. How each one is handled:

1. **Active product with zero stock** (Giannini GF-3D, id 96): treated as out of stock;
   alternatives are offered.
2. **Discontinued products** (Shelby SN-7C, id 113; Ibanez Bass 2X, id 136): not sold;
   alternatives are offered.
3. **`coming_soon` with stock** (Kala KA-ABP-CTG, id 130, stock 2): "em breve", not sold. It
   also appears in orders 3 (delivered) and 14 (pending); those are kept as historical data.
4. **Promotions**: 25 rows, only 4 active (products 90, 94, 121, 127). Inactive ones never
   change a price and are never offered. When a customer asks about one, the agent says it has
   ended and gives the current price (example 02).
5. **Two phone numbers**: (67) 3341-4444 (cover and section 1.2) vs (67) 3321-4500 (section 7).
   The official one is 3341-4444; the policy build step rewrites the other.
6. **E-mail with an accent** (`contato@empóriodamusica.com.br` in section 1.2) vs
   `contato@emporiodamusica.com.br` on the cover. The unaccented one is used.
7. **No receipt date**: return windows use `estimated_delivery` as the receipt date and today's
   system date. The agent says this is an assumption and that the team can review it.
8. **Stale orders**: the latest order is from March 2026. Pending/confirmed orders are reported
   as they are; a shipped order past its estimate is flagged as overdue and routed to the team.
9. **Orders without tracking** (confirmed/pending): the agent explains the code is sent when the
   order ships (policy 5.3).
10. **Catalog size**: the manual says "more than 300 instruments"; the data has 65. Only the data
    is used.
11. **Mixed price formats** (`799.9`, `11499`): parsed as `Decimal`, always shown as `R$ 799,90`.
12. **Descriptions that contradict the product name** in rows 131-145 (e.g. "Bateria Acústica
    Yamaha Kit 1" described as a Pearl Export; "Teclado Korg Synth 1" as a Roland with 88 keys
    while specs say 61). When a description names another brand, it is withheld from answers
    and from search; name and specs are treated as authoritative.
13. **Order totals that do not match their items**: order 3 (2 × R$ 1.749 = R$ 3.498, total
    R$ 3.450) and order 20 (R$ 1.488 vs R$ 1.400). The agent reports the stored total.
14. **Historical orders that break the installment rules**: orders 9 and 16 (6x below R$ 80)
    and 18 (12x below R$ 100). PIX orders were charged full price. New quotes follow the policy.
15. **Shared e-mail**: customers 11 and 43 have the same e-mail. Verification is against the
    order's own customer, so this cannot expose another person's order; a phone number
    disambiguates.
16. **Installment rules**: the payment table says "parcela mínima R$ 100,00" while section 3.1
    gives three brackets. Section 3.1 is applied (2-3x ≥ R$ 50, 4-6x ≥ R$ 80, 7-12x ≥ R$ 100).

Notes 12-15 are pinned by [`tests/test_data_quality.py`](tests/test_data_quality.py), so a data
change that invalidates them fails the build.

## Limitations and what I would do with more time

- **Complaints are not stored.** The agent says the complaint will be registered, as the policy
  requires, but nothing is persisted. Next step: a `register_complaint` tool writing to a ticket
  system, plus a real human handoff.
- **No evaluation suite for the LLM.** Tools are fully unit-tested, but agent behavior was
  checked by reading transcripts. Next step: a set of 30-50 scripted conversations with
  assertions on tools called and on facts in the reply (prices, deadlines, refusals), run on
  every prompt or model change. A first version of this was done by hand for the order flow
  (scenario 03 run 20 times): it went from 7/10 to 19/20 after prompt changes and an
  empty-identity guard in the tool. The remaining failure mode: the agent sometimes forgets an
  order number given in the first message and asks for it again. It never discloses data
  without verification, since that check is in code.
- **Promotion label in payment answers: 19/20.** Method: a fresh conversation per run with the
  single message "Quanto fica no PIX o [produto]?", 5 runs for each of the 4 products with an
  active promotion (Ohana CK-20, Kalani KAL-700T, Crafter HT-100, Taylor 110e). A run passed
  only if the reply contained the tool's `price_display` string verbatim, e.g.
  `R$ 439,20 (de R$ 549,00, 20% de desconto)`. Before `price_display`, with a prompt rule only,
  about half of the replies had the full label. The one miss (Taylor 110e) gave the promotional
  price without the original price and %. Next step: post-process the reply in code, so that
  any promotional price quoted without its `price_display` gets it inserted or the reply is
  regenerated. That would make the rule deterministic instead of 95%.
- **Expired promotions.** The example 02 question ("Vi que tinha uma Oferta Especial de 12%,
  ainda vale?") was run 10 times: 10/10 said clearly that it ended and gave the current price,
  none quoted the old discount. Only that scenario was measured.
- **Shipping cost is not calculated**: it needs CEP, weight and dimensions, which the data does
  not have. The agent explains the rules and refers to the team.
- **Session-only memory** and no history trimming; fine for chat sessions, not for a long-lived
  WhatsApp thread.
- **Municipal holidays and extended hours** on special dates are not modeled.
- **Alternatives** are chosen by category and price only; they do not consider string type or
  body style.
- **Observability**: no logging of tool calls, latency or token cost. In production I would log
  each turn (tools, arguments, latency, tokens) and track failure modes.
- **Production path**: a database instead of CSVs, a WhatsApp channel adapter, rate limiting,
  and embeddings-based retrieval if the policy corpus grows.

## Quality checks

- 133 `pytest` tests: every tool, the data loader, policy splitting, the agent loop (with a
  scripted fake LLM and the real tools), the CLI and the known data anomalies. No network.
- `ruff` lint and format.
- `pre-commit` runs ruff, blocks private keys, OpenAI-style API keys and `.env` files.
- GitHub Actions runs the same commands on every push, without calling the OpenAI API.

## AI coding assistants

I used AI as a team, not as autocomplete. Claude (in Cowork) analyzed the challenge and the
data with me and produced the plan; I made the calls on business rules and scope, then ran
Claude Code autonomously on the plan with explicit stop conditions. I reviewed the result with
a second, independent AI pass before publishing, which caught an evasive answer about expired
promotions and led to fixes. I also decided to keep the repository private until CI passed.

How that worked in practice:

- **Plan and rules first.** The plan fixed the architecture, project structure and commit
  sequence. The business rules (contact data, `coming_soon`, promotions, LGPD check,
  return-window date) were decided upfront. Claude Code logged its technical choices in
  [`docs/decisions.md`](docs/decisions.md) and followed [`AGENTS.md`](AGENTS.md).
- **Quality gates.** Each step had to pass `ruff` and `pytest` before its commit (enforced by
  `pre-commit`). Every tool has unit tests, and tests could not be removed, skipped or loosened
  to pass. The example conversations are generated by the real agent: when an answer was wrong,
  the agent was fixed and the examples regenerated, never edited by hand.
- **Measured, not eyeballed.** Unreliable behaviors were rerun 10-20 times before and after a fix
  (order lookup, promotion label in PIX answers, expired promotions). The numbers are in
  [Limitations](#limitations-and-what-i-would-do-with-more-time).
- **What the process caught:** an empty `OPENAI_BASE_URL` breaking the SDK, `pypdf` mangling the
  PDF, product descriptions contradicting product names, partial search results losing their
  ranking, and the model behaviors that led to switching from `gpt-4.1-mini` to `gpt-5.4-mini`.
  The second review caught the expired-promotion answer and a duplicated price in example 05.
  Prompt wording alone did not fix the promotion label, so it moved into code (`price_display`).
